# Badcase 复盘与 V1 → V2 → V2.1 迭代日志

> 所有案例均来自 `evals/reports/latest_comparison.json` 真实回归评测（DashScope `text-embedding-v3` + DeepSeek `deepseek-chat` + PostgreSQL `pgvector 0.8.7`），用于体现“评测发现问题 → 定位根因 → 架构/规则迭代 → 回归验证”的产业自升级闭环。

---

## 一、V1（纯向量基线）暴露的 4 类典型生产 Badcase

### Badcase 1：跨品评论污染触发事实幻觉（`Q02` · `PET-FOUNTAIN-PRO`）
- **现象**：买家询问不锈钢饮水机 Pro 的水箱与底座能否进洗碗机。V1 全库纯向量召回了喂食器 `PET-FEEDER-CAM` 的评论 `R4005`（“主机底座有电机绝对不能碰水”），导致模型在回答饮水机 Pro 时编造出“底座里有无线感应区和**电机部件**”（裁判 Faithfulness 扣至 `0.90`）。
- **根因**：缺乏 `sku_id` 强元数据隔离，跨品类相似词（“底座”“水洗”）污染了上下文。
- **V2 修复**：在 `pgvector` SQL 层强制 `WHERE is_active = TRUE AND sku_id = %s`；无 `sku_id` 时默认过滤 `is_accessory = FALSE`。
- **回归验证**：V2 `Q02` 的 SKU 纯净度从 `0.60` 提升至 **`1.00`**，Faithfulness 升至 **`1.00`**。

### Badcase 2：跨品评论挤占 Top-5 槽位导致关键缺陷漏召回（`Q19` · `PET-FEEDER-CAM`）
- **现象**：买家询问喂食器“语音对讲和清洗方面有没有缺点”。V1 召回 Top-5 中有 4 条来自饮水机与剃毛器（`R1002`/`R7001`/`R3002`/`R1001`），直接把喂食器自己的清洗评论 `R4005` 挤出 Top-5（Recall@5 仅 `0.50`），导致漏答“主机底座禁水”并混入其他型号塑料变形提醒（Faithfulness 仅 `0.60`）。
- **根因**：全库向量检索下，高密度清洗评论的饮水机商品在语义空间上压制了目标 SKU 的自身评论。
- **V2 修复**：单 SKU 隔离 + 中文 `jieba` BM25 词法召回 + RRF 质量加权重排。
- **回归验证**：V2 `Q19` 的 Recall@5 从 `0.50` 升至 **`1.00`**，Faithfulness 从 `0.60` 升至 **`1.00`**。

### Badcase 3：配件评论混冒主商品本体回答（`Q12` · `PET-FEEDER-CAM`）
- **现象**：买家询问喂食器自带干燥剂的使用周期与是否掉落。V1 将配件 SKU `PET-FEEDER-DESICCANT` 的评论 `R5001` 排到第 1 位并直接当成主机回答（跨型号/配件污染率 `100%`，Faithfulness `0.60`）。
- **V2 修复**：严格隔离主商品与配件评论；当本体规格与评论未覆盖干燥剂更换周期时，明确提示“现有资料未覆盖，建议人工确认”。
- **回归验证**：V2 跨型号/配件污染率从 `100%` 降至 **`0%`**，Faithfulness 从 `0.60` 升至 **`1.00`**。

### Badcase 4：无评论商品强行调用 LLM 回答（`Q13` / `Q14` / `Q15`）
- **现象**：对零评论新品 `PET-CARRIER-AIR` 和不存在的 `SKU-NON-EXISTENT-999`，V1 仍从全库硬召回 5 条无关商品评论并调用 LLM，单次耗时 `1149–2090 ms`，白白消耗输入/输出 Token（拒答边界准确率仅 `85%`）。
- **V2 修复**：在 LangGraph 状态机中增加 `grade_evidence` 证据门控节点，对零评论体验问答和空商品直接路由至 `abstain` 节点短路返回。
- **回归验证**：拒答边界准确率从 `85%` 升至 **`100%`**，拒答场景耗时降至 **`238–492 ms`**，**0 LLM Token 消耗**。

## 二、V2 回归中发现的新问题与 V2.1 迭代计划

### 观察点 1：`Q18` 冗余提示轻微拉低答案简洁度（Faithfulness `0.90` / Relevancy `0.85`）
- **现象**：在 `PET-LITTER-AUTO` 的垃圾袋问题上，评论 `R6004` 已清晰回答“不用原厂袋，普通加厚抽绳袋可套”，但 V2 Prompt 强约束导致模型在“官方参数说明”段仍输出了较长的“官方未提及该细节，建议联系人工确认”，被裁判判定略显冗余。
- **V2.1 优化方向**：在 Prompt 中区分“官方未提及但已有高赞已验证买家实测明确覆盖”与“官方与评论均未覆盖”两类场景，前者简明标注“官方未限定，买家实测可用 [Rxxxx]”，避免机械重复“联系人工确认”，同时预计可降低 15–20% 输出 Token。

### 观察点 2：V2 结构化输出带来的成本权衡与 Redis 缓存对冲
- **真实数据**：20 题评测中，V2 因分段结构与引用标注更详尽，预估千次问答模型成本略高于 V1（`¥3.033` vs `¥2.170`）。
- **工程对冲手段**：引入 Redis 问答缓存（TTL 600s）后，实测高频重复问题耗时从 `4757 ms` 降至 **`30 ms`（-99.4%）**，且热点命中完全 **0 Token**；结合拒答短路节点，在线上高频导购场景中可将综合成本压低至基线以下。

### 观察点 3：工程接入踩坑记录
- **DashScope `text-embedding-v3` 批量上限**：入库初版 `batch_size=16` 触发 `400 InvalidParameter (batch size should not be larger than 10)`，调整分批大小为 `10` 并增加维度强校验，避免静默写入错误维度。
- **Langfuse v2 服务端与新版 SDK 兼容**：虚拟机部署 `langfuse:2`（`2.95.11`），而本地安装的 `langfuse` Python SDK 为 `5.2.0`（已移除 v2 `.trace()` 接口）；改为直调标准 `/api/public/ingestion` 批量接口，稳定上报 Trace、Span、Generation（含 Token）及 `citation_valid` / `user_feedback` 评分。
