## 二、业务应用场景与核心痛点

### 1. 目标用户与典型使用场景
1. **售前客服 / 导购辅助查证（高频实时场景）**
   - **背景**：在亚马逊/跨境独立站售卖宠物智能硬件（饮水机、喂食器、全自动猫砂盆、低噪剃毛器）时，商品详情页通常只写宣传参数，买家真正关心的是真实使用体验细节，例如：
     - 饮水机放卧室床头晚上到底吵不吵？硬水地区用久了水泵会不会变响？底座能不能进洗碗机？
     - 家里路由器是 5GHz 双频合一，自动喂食器能不能连上？混超过 12mm 的大块鸡胸肉冻干会不会卡粮？停电装电池时摄像头还能不能看？
     - 9kg 缅因猫和 1.2kg 幼猫能不能安全使用自动猫砂盆？3mm 粗条豆腐砂和松木砂会不会卡机或误铲？
   - **传统痛点**：客服手动翻几百条评论响应太慢；凭印象口头承诺又极易引发退货、1 星差评和客诉。
   - **系统价值**：客服系统接入 `/api/v1/qa` 接口（自动传入当前咨询商品的 `sku_id`），2 秒内拿到**明确区分“官方规格”与“买家实测”**的答案，每条买家结论强制附带 `[Rxxxx]` 评论编号，下方直接展示原评论让客服核对后再发给买家。
2. **选品运营 / 差评复盘与研发调试（中台分析场景）**
   - 运营可围绕具体 SKU 快速检索买家痛点、核对正负反馈覆盖是否充分（单条评论时系统会主动提示“样本量偏少”）。
   - 前端控制台同时提供 **V1 基线版 vs V2 生产版同屏双栏对比**、分阶段耗时拆解和 **Badcase 一键点踩回流**，便于算法/研发团队演示、排错与持续迭代。

### 2. 为什么普通大模型 / 普通向量 RAG 在电商场景会翻车？
- **痛点 1（数据脏乱）**：电商评论充斥大量“很好”“ok good”“物流很快还没拆开用”等无体验价值水评及刷单重复片段，直接入库会稀释向量检索质量并白烧 Token。
- **痛点 2（同品牌多型号 & 配件高度共用关键词，极易串品）**：例如 `PET-FOUNTAIN-PRO`（304 不锈钢无线泵饮水机）、`PET-FOUNTAIN-LITE`（塑料有线基础款）和 `PET-FOUNTAIN-FILTER`（专用替换滤芯）标题都包含“PurrFlow”“静音”“饮水机”。纯向量全库检索会把 Lite 的差评（“嗡嗡响、长黑下巴”）或配件评论混进 Pro 的上下文里，导致严重答错或事实幻觉。
- **痛点 3（零评论新品与未知型号硬编造）**：新品刚上架暂无评论（如 `PET-CARRIER-AIR` 航空宠物包），普通 RAG 会强行召回其他商品的评论凑数并照常调用大模型，既费钱又容易瞎编。
- **痛点 4（一次交付无法迭代）**：没有黄金评测集、没有线上监控和点踩回流机制，改一次 Prompt 不知道整体是变好还是变差。

## 三、系统整体架构与工程设计

### 1. 核心数据链路（8 步产业自升级闭环）
1. **数据治理流水线（`src/ecom_rag/governance.py` & `ingest.py`）**
   - 文本空白归一化 → 过滤 `<12` 字符的短评 → 过滤“纯物流/未拆封”水评（同时保护既夸物流又含真实体验词的评论不被误杀）→ 拦截无主数据的孤儿 SKU → 按 `(sku_id, normalized_text)` 做 SHA-256 去重。
   - 综合质量打分（0~1）：综合文本信息密度（40%）、是否已验证购买 `verified_purchase`（25%）与对数缩放后的有用票数 `helpful_votes`（35%）。
   - 单 SKU 样本上限控制：按质量得分降序截断，防止爆款商品评论刷爆索引与入库成本。
   - 增量同步与软删除（`db.py`）：PostgreSQL + `pgvector` HNSW 索引（`m=16, ef_construction=64`），使用 `ON CONFLICT (sku_id, content_hash) DO UPDATE` 幂等写入，并对源数据中已下架/删除的旧评论执行 `is_active = FALSE` 逻辑软删除。
2. **双版本检索架构（`src/ecom_rag/retriever.py`）**
   - **V1 纯向量基线（对照组）**：全库纯向量 cosine Top-5，不做 `sku_id` 强过滤、不排除配件、无词法召回与重排。
   - **V2 混合检索与质量重排**：
     - SQL 层强元数据隔离：传入 `sku_id` 时严格 `WHERE is_active = TRUE AND sku_id = %s`；未传 `sku_id` 时默认过滤 `is_accessory = FALSE` 排除配件干扰。
     - 双路召回：在受控候选池上结合 `pgvector` 余弦语义召回 + `jieba` 中文分词 `BM25Okapi` 词法召回（精准命中 `2.4GHz`、`304`、`1.5mm`、`IPX7` 等规格词）。
     - **RRF 融合 + 质量加权重排**：`final_score = 0.55 * norm_rrf + 0.30 * vector_score + 0.15 * quality_score + verified_boost(0.05)`。
3. **LangGraph Agentic RAG 状态机（`src/ecom_rag/graph.py`）**
   - 节点编排：`START → retrieve → grade_evidence → [abstain | generate → verify_citations] → END`。
   - **证据充分性门控（`grade_evidence`）**：
     - 商品与评论均缺失 → 路由至 `abstain`；
     - 有商品规格但零评论，且用户问的是真实使用体验/评价/口碑 → 路由至 `abstain`（0 LLM Token 短路拒答）；
     - 语义分、综合分、BM25 分均低于阈值 → 路由至 `abstain`；
     - 独立评论数 `< 2` 时透传“样本量偏少”风险提示。
   - **结构化分离生成（`generate`）**：将 `products.specs_json`（官方规格）与召回评论（买家实测）分块拼装，Prompt 强制分段表述、正负面客观并陈、每条评论结论必须附 `[Rxxxx]` 编号。
   - **引用核验后置守卫（`verify_citations`）**：正则提取回答中的所有 `[Rxxxx]`，逐一校验是否属于本轮召回集合；若检出伪造引用则标记 `citation_valid = False` 并附加系统提醒。
4. **网关保护、缓存与可观测闭环（`api.py`、`cache.py`、`observability.py`）**
   - **Redis 固定窗口限流**（默认 30 次/分钟/IP）防止高频刷接口；
   - **Redis 热点问答缓存**（按 `pipeline_version + sku_id + 归一化问题` 哈希，TTL 600s）；
   - **双写审计与 Langfuse 看板**：每次请求写入 PostgreSQL `qa_feedback_logs`（含分阶段耗时与 Token），并通过 Langfuse `/api/public/ingestion` 批量接口上报 Trace、Retrieval Span、Generation（含 Token 用量）及 `citation_valid` 评分；
   - **Badcase 反馈回流（`/api/v1/feedback`）**：支持用户提交满意/不满意及分类标签（`wrong_sku` / `hallucination` / `missed_recall` / `over_abstain`），同时回写数据库与 Langfuse `user_feedback` Score。

## 五、真实遇到的难题、难点与踩坑复盘（面试加分核心）

### 难点 1：跨品评论引发的隐蔽“事实拼贴幻觉”（Badcase `Q02`）
- **遇到的问题**：在评测 `Q02`（问不锈钢饮水机 Pro 底座能否进洗碗机）时，V1 全库纯向量把自动喂食器 `PET-FEEDER-CAM` 的评论 `R4005`（“主机底座有电机绝对不能碰水”）召回进来。模型把两款产品的信息拼在一起，回答饮水机 Pro 时编造出“底座里有无线感应区和**电机部件**”（实际 Pro 是磁感应底座无内置电机），Faithfulness 掉到 `0.90`。
- **解决与收益**：V2 在数据库检索层强制 `sku_id` 强过滤，彻底切断跨品信息流入上下文，复测 `Q02` 纯净度与忠实度双双达到 `1.00`。

### 难点 2：跨品高密度评论挤占 Top-5 导致关键缺陷漏召回（Badcase `Q19`）
- **遇到的问题**：在评测 `Q19`（问喂食器“语音对讲和清洗方面有什么缺点”）时，V1 召回的 Top-5 中有 4 条来自饮水机和剃毛器的清洗评论，直接把喂食器自己的清洗评论 `R4005` 挤出了 Top-5（Recall@5 仅 `0.50`），导致漏掉“底座禁水”这一致命售后注意点（Faithfulness 仅 `0.60`）。
- **解决与收益**：通过单 SKU 隔离 + 中文 BM25 词法召回 + RRF 重排，`Q19` 精准召回 `R4004` 和 `R4005`，Recall@5 与 Faithfulness 均从 `0.50/0.60` 提升至 `1.00`。

### 难点 3：质量提升 vs 输出 Token 成本增加的工程权衡（以及 `Q18` 冗余提示）
- **遇到的问题**：V2 要求分段输出“官方规格 + 买家实测 + `[Rxxxx]` 引用 + 缺失提醒”，20 题总输出 Token 从 2054 增至 4292，预估千次问答成本从 ¥2.170 升至 ¥3.033；同时在 `Q18`（猫砂盆垃圾袋问题）上，虽然评论 `R6004` 已经明确回答“普通抽绳袋可用”，但模型仍在官方规格段输出了一句冗长的“建议联系人工确认”，拉低了 Relevancy（`0.85`）。
- **解决与迭代思路**：
  1. 工程侧用 **证据门控 0 Token 拒答短路**（省掉无解问题的 LLM 调用）+ **Redis 热点缓存**（实测冷请求 4757ms → 热缓存 30ms、0 Token）对冲高频导购场景成本；
  2. Prompt 侧规划 V2.1 迭代：区分“官方未限定但已有高赞已验证实测覆盖”与“双边均未覆盖”，减少冗余拒答话术，预计可再降 15%–20% 输出 Token。

### 难点 4：第三方模型 API 与自托管可观测组件的版本踩坑
1. **DashScope `text-embedding-v3` 批量上限坑**：初版入库设 `batch_size=16`，调用直接报 `400 InvalidParameter: batch size should not be larger than 10`。排查后改为 `batch_size=10` 分批请求，并在客户端加入返回向量维度与 `pgvector` 定义维度（1024）的强一致校验，防止静默写脏库。
2. **Langfuse v2 服务端与 Python SDK v5 不兼容坑**：虚拟机用 Docker 部署了轻量级的 `langfuse:2`（`2.95.11`），但 `uv` 安装的 `langfuse` Python SDK 默认是 `5.2.0`（已移除旧版 `.trace()` 方法并切向 OTel 协议）。排查 `dir(Langfuse)` 确认差异后，改为通过 `httpx` 直调 Langfuse 标准 `/api/public/ingestion` 批量 REST 接口，同时上报 Trace、Span、Generation（含 Token）以及 `citation_valid`、`user_feedback` Score，既不降级环境又能稳定观测。
3. **测试隔离与跨平台环境坑**：本机系统默认 Python 3.14 存在部分 AI 生态包预编译兼容风险，使用 `uv` 锁定 Python 3.12 虚拟环境；同时将基础组件（PostgreSQL+pgvector、Redis、Langfuse）部署在 EL10 Linux 虚拟机 Docker Compose 中，解决 Windows 本地多中间件运维问题，并通过 9 项离线单元测试保证无外网时也可验证核心治理与状态机逻辑。

## 六、高频面试追问标准应答库（供面试 Agent 直接检索）

**Q1：这个项目是你公司真实上线的，还是个人项目？**
> 答：坦诚说明，这是我结合之前在杭州宠品家跨境宠物电商做选品和评论分析时的真实业务痛点，独立设计并完整落地的个人开源工程项目。代码、Docker 编排、20 题评测脚本、V1/V2 实测对比报告和 Langfuse 追踪链路全部可公开核验，也可以现场启动演示。

**Q2：为什么选 PostgreSQL + pgvector 而不是专门的向量数据库（如 Milvus / Qdrant）？**
> 答：电商商品问答天然强依赖“结构化元数据过滤（`sku_id`、`is_accessory`、`is_active`、商品规格 JSONB）+ 向量检索 + 事务一致性”。用 PostgreSQL + `pgvector`（HNSW 索引）可以在同一条 SQL 里完成过滤和向量召回，无需维护两套数据库的数据双写同步，运维复杂度更低，中小规模电商（百万级评论以内）性价比和一致性最好；如果后续评论规模上亿、QPS 极高，再考虑读写分离或拆专业向量库。

**Q3：为什么在向量检索之外还要加 BM25 和 RRF 重排？**
> 答：电商问答里有大量精确型号、数字规格和专有词（如 `2.4GHz`、`304不锈钢`、`1.5mm`、`IPX7`、`5-12mm`）。纯稠密向量擅长语义泛化，但对这类精确词有时区分度不够；BM25 擅长精确词匹配，结合 RRF（Reciprocal Rank Fusion）无需调敏感的线性权重即可稳定融合两路排名，再叠加评论质量分（长度、已验证购买、有用票数），能把高可信度、含具体参数的实测评论顶到最前面。

**Q4：你怎么防止大模型“胡说八道”或把别的商品的缺点安在当前商品上？**
> 答：做了四层防线：
> 1. **检索前强隔离**：SQL 层严格按 `sku_id` 过滤，未传 SKU 时默认排除 `is_accessory=TRUE` 的配件；
> 2. **生成前证据门控**：在 LangGraph 里加 `grade_evidence` 节点，零评论体验问题或相关性全低于阈值时直接走 `abstain` 节点短路拒答（0 Token）；
> 3. **生成中结构化约束**：Prompt 强制分离“官方参数说明”和“买家实测反馈”，每条体验结论必须附 `[Rxxxx]` 编号；
> 4. **生成后引用核验**：`verify_citations` 节点用正则提取所有 `[Rxxxx]`，核对是否都在本轮召回列表内，检出伪造编号直接拦截提示。

**Q5：你怎么做 RAG 评测？如何证明 V2 真的比 V1 好？**
> 答：我没有靠肉眼看一两条例子拍脑袋，而是建了 20 题覆盖 4 类场景（正常问答、跨品陷阱、拒答边界、正负权衡）的黄金评测集，把评测拆成三类指标自动化回归：
> 1. **确定性检索指标**：SKU 纯净度（44%→100%）、跨品污染率（100%→0%）、必需评论 Recall@5（96.9%→100%）；
> 2. **安全护栏指标**：拒答准确率（85%→100%）、引用合法率（100%）；
> 3. **LLM-as-a-Judge 质量指标（RAGAS 口径）**：Faithfulness（0.930→0.995）、Answer Relevancy（0.953→0.983），同时记录 P50/P95 延迟与千次成本，确保每次改动有据可查。

**Q6：线上运行后，如果发现新的 Badcase 怎么持续迭代（产业自升级闭环）？**
> 答：全链路都留了可追溯锚点：每次问答生成唯一 `trace_id`，同时落 PostgreSQL `qa_feedback_logs` 和 Langfuse（记录分阶段耗时、Token 和 `citation_valid`）。客服或运营在前端点踩并打上 `wrong_sku / hallucination / missed_recall / over_abstain` 标签后，反馈同步写回数据库和 Langfuse Score。我们定期按标签拉取 Badcase 沉淀进 `golden_dataset.json`，针对性调整数据清洗规则、检索参数或 Prompt，再重跑 `evals/run_eval.py` 确认新指标提升且老用例无回归后才发布。

**Q7：如果这个系统要真正上线承载高并发（比如几百个客服同时用），你还会做哪些生产加固？**
> 答：主要补四个方面：
> 1. **检索性能**：把目前在候选池内实时计算的 BM25 切换为 PostgreSQL 原生 `tsvector` + `pg_search`/中文分词索引或 Elasticsearch 混合检索，减少应用层内存开销；
> 2. **语义缓存升级**：目前 Redis 是归一化文本精确缓存（热命中 30ms），线上可升级为基于向量相似度的语义缓存，进一步提高命中率；
> 3. **数据管道异步化**：评论采集、清洗和向量化改为消息队列（如 RabbitMQ/Kafka）异步消费 + 定时增量同步，支持评论删除/修改实时失效对应缓存；
> 4. **发布与灰度**：结合 Langfuse Prompt Management 做 Prompt 版本管理与 A/B 灰度分流，配置 P95 延迟、错误率与日 Token 预算告警，异常时一键回滚上一版配置。

**Q8：你为什么要做这个个人开源项目？（考察自驱力与业务洞察）**
> - **应答结构（4 步逻辑）**：真实工作痛点 → 原公司客观条件受限 → 主动按生产级闭环做工程验证 → 沉淀为可复现能力反哺新岗位。
> - **避坑红线（切忌回答）**：不要说“为了找工作刷简历/跟着教程练手”，也不要只说“大模型很火想学框架”。
> - **标准口语应答**：
>   > “动机直接来自我在跨境宠物电商工作时遇到的真实痛点。当时无论是售前咨询还是选品复盘，经常要从大量买家评论里核对详情页没写清的细节——比如饮水机放卧室吵不吵、5GHz 路由器连不连得上、配件和主商品怎么区分，靠人工翻太慢，直接套普通 RAG 又特别容易串型号和瞎编。在中小公司日常节奏下，当时只能做很轻量的辅助脚本先把眼下问题应付过去，没有条件去搭规范的混合检索、黄金评测集、Redis 缓存和 Langfuse 可观测监控。但我自己一直想按**生产级 AI 应用的标准**把这条真实业务闭环完整跑通，用实测数据验证几个工程问题——比如纯向量检索串品到底有多严重、证据门控拒答能省多少无效 Token、结构化引用带来的成本增幅怎么用缓存对冲、怎么靠 Badcase 回流持续迭代。所以我用脱敏重构的数据把它做成了可复现的开源工程。把跨品幻觉、API 批量限流、监控版本兼容这些真坑都亲手踩完之后，后续在团队里做类似垂直领域的 RAG 或 Agent 落地，我就不需要从零摸索，能直接按这套工程规范上手。”
